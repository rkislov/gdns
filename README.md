# GHole

DNS-сервер на Go с локальными зонами, рекурсивным резолвером, split DNS и фильтрацией доменов. Веб-интерфейс собран с Tailwind CSS и встроен через `go:embed`. Поставка — один бинарник; Node.js, внешний веб-сервер и отдельный процесс базы данных для SQLite не нужны. Для PostgreSQL нужен доступный сервер PostgreSQL.

**Статус: рабочая первая версия для разработки и проверки в тестовой сети.** Это ещё не готовая замена Pi-hole / Unbound / BIND для промышленной эксплуатации. Внешние ответы проверяются локальным DNSSEC-валидатором; подписание собственных зон пока не реализовано.

## Быстрый запуск

Требуется Go 1.27+ для сборки:

```sh
make build
./bin/ghole -config ./ghole.json
```

Первый запуск инициализирует SQLite (`ghole.json.db`) из существующего `ghole.json` либо встроенных значений и создаёт случайный административный токен. После инициализации источником настроек является база; JSON используется только для начального импорта, явного повторного импорта и экспорта. По умолчанию:

- DNS UDP/TCP: `127.0.0.1:1053` — запуск без root и без конфликта с mDNS на 5353.
- Веб-интерфейс: http://127.0.0.1:8080.
- Токен: `ghole.json.token` рядом с конфигурацией, права `0600`.
- Режим: собственная рекурсия от корневых серверов, без внешнего рекурсивного резолвера.

```sh
cat ghole.json.token
dig @127.0.0.1 -p 1053 router.home.arpa A
dig @127.0.0.1 -p 1053 example.com A
dig @127.0.0.1 -p 1053 example.com A +tcp
./bin/ghole -config ./ghole.json -check
```

Можно передать существующий токен через `GHOLE_ADMIN_TOKEN` (не менее 24 символов). Не добавляйте токены и конфигурацию с секретами подписок в Git.

Для обслуживания LAN измените `dns_listen` на адрес интерфейса и нужный порт, обычно 53, в разделе настроек веб-интерфейса и перезапустите процесс. Порт 53 может требовать права или capability ОС. `allowed_clients` определяет разрешённые CIDR, независимо от адреса прослушивания. У веб-интерфейса по умолчанию только локальный доступ; для удалённого администрирования используйте HTTPS reverse proxy или SSH-туннель.

## Что работает

- DNS по UDP и TCP, ограничение размера UDP-ответов и переход на TCP при усечённом upstream-ответе.
- Режимы `recursive` (итеративный обход от root) и `forward` (на заданные upstream IP:port).
- `primary`: локальные IN-зоны с SOA, типизированными записями, wildcard, NXDOMAIN/NODATA, empty non-terminals и NS-делегациями. В локальной зоне CNAME возвращается как авторитетный ответ; дополнительное разрешение его цели клиент делает отдельным запросом.
- `forward`: пересылка выбранной зоны на рекурсивные серверы с RD=1.
- `stub`: начальные адреса авторитетных серверов зоны; запросы с RD=0 и последующий обход делегаций. Перечень серверов задан явно, автоматическое обновление stub NS ещё не реализовано.
- Split DNS для всех типов зон по реальному адресу источника, IPv4/IPv6 CIDR. ECS не используется для выбора представления.
- Импорт/экспорт BIND9 **zone master files**: `$ORIGIN`, `$TTL`, многострочные SOA, относительные имена. `$INCLUDE` отключён. `named.conf`, BIND views и параметры сервера не импортируются. Экспорт zone file содержит общие записи выбранной зоны; CIDR и сплит-группы сохраняются полным JSON-экспортом.
- Ручные блокировки, URL-фиды, HTTPS-подписки с заголовком `Authorization`, офлайн-загрузка текстового или gzip-файла. Форматы: домен на строку, hosts (несколько доменов на строку), простые правила `||domain^`. Полный синтаксис Adblock не поддерживается: неподдерживаемые строки отклоняются.
- Настройки зон, CIDR, фильтров, upstream, кеша и режима через веб; применение без перезапуска. Адреса прослушивания и TLS меняются с перезапуском; интерфейс показывает ожидающие применения изменения. Валидация до сохранения, SQL-транзакция, ETag и ревизия базы для защиты от перезаписи чужих изменений.
- Счётчики и кольцевой журнал в памяти (по умолчанию 10 000 запросов, настраивается от 100 до 100 000) с пагинацией и выбором 10/25/50/100 строк. Журнал можно отключить в настройках.

Веб-интерфейс не использует CDN, внешние шрифты или внешние скрипты. Tailwind CSS уже собран и находится в репозитории. Для изменения стилей:

```sh
npm ci
npm run css
make build
```

## SQLite и PostgreSQL

По умолчанию используется SQLite без CGO: один файл базы рядом с конфигурационным префиксом. Включены WAL, `synchronous=FULL` и busy timeout. Файл базы создаётся с правами `0600`.

```sh
./bin/ghole -storage sqlite -database ./ghole.db
```

Для крупной установки выберите PostgreSQL. Строку подключения лучше передавать через окружение, чтобы пароль не попадал в список аргументов процесса:

```sh
export GHOLE_DATABASE_URL='postgres://ghole:password@db.example/ghole?sslmode=verify-full'
./bin/ghole -storage postgres
```

Пользователю PostgreSQL нужны права на создание таблиц и индексов в выделенной базе/схеме. Таблицы создаются автоматически. Используйте отдельную роль с минимально необходимыми правами и доверенный TLS-сертификат сервера БД.

Зоны и их представления хранятся в `ghole_zones`, отдельные записи — в `ghole_records` (owner, тип, TTL и BIND-представление), фиды — в `ghole_feeds` / `ghole_feed_domains`, блокировки — в `ghole_blocked`. Настройки и версия схемы — в `ghole_state`. Индекс `(zone_id, owner, rrtype)` позволяет адресовать записи в SQL. DNS-ядро при запуске загружает подготовленные индексы в память и не выполняет SQL на каждый DNS-запрос.

Сохранение использует транзакцию и проверку ревизии. Неизменившиеся наборы записей и доменов фидов не переписываются; изменённые вставляются пакетами. На данный момент предполагается один активный процесс GHole на базу. Несколько процессов не синхронизируют DNS-снимки автоматически; устаревший писатель получит ошибку конфликта и должен перезапуститься. Сам выбор PostgreSQL ещё не означает поддержку HA-кластера.

Перенос из SQLite в PostgreSQL (производите при остановленных изменениях настроек):

```sh
./bin/ghole -storage sqlite -database ./ghole.db -export-config ./ghole.private.json
# GHOLE_DATABASE_URL уже содержит строку подключения к целевой базе
./bin/ghole -storage postgres -config ./ghole.private.json -import-config -check
```

`-import-config` явно заменяет данные выбранной базы. Без этого флага существующая база имеет приоритет над JSON. Экспорт включает записи, фиды и секреты подписок; файл создаётся с правами `0600`. Токен веб-администратора в этот экспорт не включается. Для обычных резервных копий используйте SQLite backup API / остановленный процесс либо `pg_dump`; не копируйте только основной SQLite-файл во время работы WAL.

## DoH и DoT

В разделе «Настройки → Адреса и шифрование» задайте отдельные адреса DoH/DoT и пути к PEM-сертификату и приватному ключу. Изменения сохраняются в БД, после них нужен перезапуск. Пустой адрес отключает транспорт. Сертификат должен быть доверенным клиентам и соответствовать DNS-имени сервера. Автоматический выпуск / продление сертификатов пока отсутствует.

Пример полей конфигурации для первоначального импорта:

```json
{
  "doh_listen": "0.0.0.0:443",
  "dot_listen": "0.0.0.0:853",
  "tls_cert_file": "/etc/ghole/fullchain.pem",
  "tls_key_file": "/etc/ghole/privkey.pem"
}
```

Это **входящие серверные транспорты**. Upstream-пересылка в этой версии по-прежнему использует обычный DNS UDP/TCP.

- DoH: HTTPS `/dns-query`, HTTP/2, GET с `dns=` (base64url без padding) и POST с `application/dns-message`.
- DoT: DNS wire format с двухбайтовой длиной поверх TLS, постоянные соединения.
- Минимум TLS 1.2. DoH-путь размещён отдельно от веб-администрирования и не требует административного токена.
- Для всех транспортов работают одни ACL, split DNS, блокировки, кеш, счётчики и журнал.
- Для выбора представления используется реальный IP соединения; `X-Forwarded-For` и ECS не принимаются как доверенный адрес клиента. При размещении за reverse proxy клиентом для ACL будет сам прокси.

## Обзор, графики и Prometheus

Обзор показывает CPU, число логических ядер, версию ядра ОС, занятую/доступную оперативную память и файловую систему с данными GHole. Это показатели хоста, на котором работает процесс; они не означают статистику удалённого PostgreSQL-сервера. Для другого раздела диска используйте `-metrics-disk-path /data`.

Системные показатели собираются в фоне каждые 5 секунд. Графики показывают количество завершённых запросов и блокировок за интервал, а также среднее время обработки DNS в миллисекундах. Заблокированные запросы — обращения к именам из чёрного списка, включая заблокированные CNAME-цели, а не количество строк фида. Время включает разрешение имени и поиск в кеше, но не сетевую запись ответа. Интервал без запросов не получает выдуманное значение задержки.

История ограничена 180 точками (примерно 15 минут) и хранится в памяти, после перезапуска очищается. Для долгосрочной истории и перцентилей используйте Prometheus. Графики не зависят от включения журнала запросов.

По умолчанию exporter доступен на `http://127.0.0.1:9090/metrics`. Он работает на отдельном адресе без административного токена. Меняйте адрес через `-metrics-listen`; пустая строка отключает exporter. Если открываете endpoint в сети, ограничьте доступ сетью мониторинга / firewall.

```yaml
scrape_configs:
  - job_name: ghole
    scrape_interval: 15s
    static_configs:
      - targets: ['127.0.0.1:9090']
```

Основные метрики:

- `ghole_dns_queries_total{transport,result}` — завершённые DNS-запросы.
- `ghole_dns_blocked_total{transport}` — блокировки чёрного списка.
- `ghole_dns_response_duration_seconds_bucket`, `_sum`, `_count` с меткой `transport` — гистограмма времени обработки.
- `ghole_system_cpu_usage_ratio`, `ghole_system_logical_cpus`, `ghole_system_info{os,kernel_version}`.
- `ghole_system_memory_total_bytes`, `_used_bytes`, `_available_bytes`.
- `ghole_system_disk_total_bytes`, `_used_bytes`, `_free_bytes`.
- `ghole_system_metrics_success`, `ghole_system_sample_timestamp_seconds` — доступность и свежесть системных показателей.
- Стандартные `go_*` и доступные на платформе `process_*`.

Метки ограничены транспортами `udp`, `tcp`, `doh`, `dot` и фиксированным набором результатов; доменов и IP клиентов в метках нет.

Примеры PromQL:

```promql
sum(rate(ghole_dns_queries_total[5m]))
sum(rate(ghole_dns_blocked_total[5m]))
histogram_quantile(0.95, sum by (le) (rate(ghole_dns_response_duration_seconds_bucket[5m])))
```

## Правила выбора зоны

1. Проверка `allowed_clients`.
2. Поиск наиболее конкретного суффикса зоны, для которого есть подходящее представление.
3. Внутри одного имени зоны — самый длинный подходящий CIDR; без CIDR — общее представление.
4. Локальная primary-зона имеет приоритет над фильтрацией. Для forward/stub и внешних имён применяется блокировка; затем кеш и разрешение.

Две зоны с одинаковым именем и одинаковым CIDR не допускаются. Также не допускаются два общих представления одного имени. Конфигурация с более конкретной зоной без подходящего представления позволяет поиск подходящей родительской зоны. Кеш разделён по выбранному представлению и DO/CD; при изменении конфигурации создаётся новый кеш.

Пример двух представлений (фрагмент массива `zones`):

```json
[
  {
    "name": "corp.example.",
    "kind": "primary",
    "clients": ["10.20.0.0/16"],
    "records": [
      "corp.example. 300 IN SOA ns.corp.example. hostmaster.corp.example. 1 3600 600 86400 60",
      "app.corp.example. 300 IN A 10.20.0.10"
    ],
    "servers": []
  },
  {
    "name": "corp.example.",
    "kind": "forward",
    "clients": [],
    "records": [],
    "servers": ["1.1.1.1:53", "9.9.9.9:53"]
  }
]
```

## Сплит отдельных записей в одной зоне

Primary-зона может содержать общие `records` и несколько `record_views`. Каждая группа задаёт CIDR источников и переопределяемые записи BIND9. Дублировать SOA, NS, MX и остальные общие записи для каждой сети не нужно.

```json
{
  "name": "corp.example.",
  "kind": "primary",
  "clients": [],
  "servers": [],
  "records": [
    "corp.example. 300 IN SOA ns.corp.example. hostmaster.corp.example. 1 3600 600 86400 60",
    "corp.example. 300 IN NS ns.corp.example.",
    "ns.corp.example. 300 IN A 192.0.2.53",
    "app.corp.example. 300 IN A 192.0.2.10"
  ],
  "record_views": [
    {
      "clients": ["10.1.2.0/24"],
      "records": ["app.corp.example. 300 IN A 10.1.2.10"]
    },
    {
      "clients": ["10.1.2.16/28"],
      "records": ["app.corp.example. 300 IN A 10.1.2.17"]
    }
  ]
}
```

Для `10.1.2.16–10.1.2.31` выбирается `/28`; соседние `.15` и `.32` используют `/24`, прочие разрешённые клиенты — общую запись. Поддерживаются любые IPv4-префиксы `/0…/32` и IPv6 `/0…/128`, включая правила для одного адреса.

Переопределяется целиком RRset (имя + тип), а не одна строка из набора. Более конкретные CIDR наследуют не переопределённые типы от менее конкретных правил и общих записей. Например, свой A не меняет общий AAAA. CNAME исключает другие типы того же имени в выбранном представлении; более конкретный A может заменить наследуемый CNAME. Запись, существующая только в приватной группе, не видна остальным клиентам. Общая SOA обязательна; внутри `record_views` SOA запрещена.

В веб-редакторе зоны есть отдельный раздел «Сплит-записи внутри зоны». Эти записи хранятся отдельно в `ghole_record_views` / `ghole_view_records` с индексом по зоне, группе, имени и типу. Схема базы автоматически обновляется с версии 1 до 2 без удаления общих записей. Выбор клиента и объединение RRset подготовлены при применении конфигурации; на запросе нет обращения к SQL.

## Журнал и пагинация

В разделе журнала доступны 10, 25, 50 и 100 строк на страницу, переходы назад/вперёд и кнопка обновления. При просмотре фиксируется ID последней записи выборки: новые запросы не сдвигают страницы. Старые строки могут исчезнуть при вытеснении из ограниченного кольцевого буфера; журнал не является архивом и не сохраняется после перезапуска.

`query_log_limit` настраивается в веб-интерфейсе; по умолчанию 10 000, допустимо 100–100 000. Отключение `query_log` не отключает счётчики, графики и Prometheus. `/api/status` возвращает только последние 8 строк для обзора; `/api/logs?page=1&page_size=25` возвращает страницу, общее число доступных строк, число страниц и `anchor`. Для следующих страниц передавайте полученный `anchor`.

## Фиды и feed.kislovs.ru

Создайте источник в разделе «Фиды и блокировки». Для загрузки по подписке укажите точный URL, выданный поставщиком, и значение `Authorization`, если оно требуется. Секреты разрешены только с HTTPS; переход с секретом на другой origin запрещён. Для офлайн-источника оставьте URL пустым и загрузите файл. Лимит распакованного списка — 32 MiB / 1 миллион доменов на импорт. Ошибочная загрузка не заменяет текущий список.

В этой версии обновление запускается кнопкой или API, автоматического расписания пока нет. Списки сохраняются в отдельных таблицах базы и работают после перезапуска без доступа к провайдеру. Собственные зоны имеют приоритет; блокируются домен и его поддомены. CNAME на заблокированное имя в ответе upstream также блокируется.

Специальный протокол `feed.kislovs.ru`, выдача подписок, подписи и формат фирменного офлайн-пакета **не подтверждены**. Универсальный загрузчик совместим только при выдаче поддерживаемого текстового формата / gzip. Для специального API нужен образец ответа или документация поставщика.

## Производительность и ограничения

Путь DNS-запроса использует неизменяемые подготовленные индексы и атомарный указатель на конфигурацию. Выбор CIDR использует индекс префиксов по длине, поиск блокировки — хеш-индекс суффиксов; количество записей фида не требует линейного перебора. Структура пустых узлов primary-зоны подготовлена заранее.

Кеш разделён на 64 сегмента, ограничен числом записей, уменьшает TTL и копирует ответы перед возвратом. Есть положительное и отрицательное кеширование (отрицательные ответы только с SOA). Одновременные промахи для одного ключа объединяются через singleflight. Не более 256 активных внешних разрешений; бюджет одного разрешения — 6 секунд / 80 UDP-обменов, глубина зависимостей 12, делегаций 32. Повтор по TCP идёт в рамках того же контекста.

```sh
make test
make bench
```

Бенчмарки измеряют внутренний `Resolve` параллельно, без сокетов, сериализации DNS, HTTP и журнала. Они не являются измерением сетевого QPS или p99. Для оценки под нагрузкой нужны dnsperf/resperf, разные hit ratio, реальные распределения имён, DNSSEC и профили CPU/heap. Отключите `query_log` для максимальной пропускной способности.

Текущий итеративный резолвер является базовой реализацией: кешируются конечные ответы, отдельного кеша делегаций/NS-адресов и постоянных соединений к upstream пока нет. Поэтому холодная рекурсия заметно дороже попадания в кеш. Не реализованы prefetch, serve-stale, RRL по клиентам, расширенная защита от cache poisoning и промышленное управление отрицательным кешем. Нужна отдельная нагрузочная и протокольная проверка перед публичной эксплуатацией.

## DNSSEC: локальная валидация

В **Настройки → DNSSEC** включается локальная проверка внешних ответов в recursive, forward и stub режимах. AD upstream-сервера не используется как доказательство. Валидатор строит цепочку от доверенного DS/DNSKEY через подписанные DS и DNSKEY к RRSIG каждого RRset. Проверяются время действия подписей, CNAME/DNAME, wildcard, NXDOMAIN/NODATA, NSEC и NSEC3, включая opt-out. Подтверждённые неподписанные делегации обслуживаются без AD; ошибочные или неполные доказательства дают SERVFAIL и EDNS Extended DNS Error.

Веб-панель позволяет менять доверенные DS/DNSKEY, исключения для частных суффиксов, учёт CD клиента, лимит итераций NSEC3 и тайм-аут. Изменения сохраняются в SQLite/PostgreSQL и применяются без перезапуска с новым поколением кеша. Начальные корневые DS IANA включают KSK-2017 и KSK-2024. Кнопка загрузки IANA получает актуальный XML по HTTPS с проверкой сертификата и помещает DS в редактор; администратор проверяет и сохраняет изменения. **Автоматическое сопровождение корневых trust anchors по RFC 5011** включается в том же разделе. Оно использует DNSKEY-ответы, проверенные текущими ключами, и собственное постоянное состояние в SQL. Загрузка IANA остаётся средством первоначального bootstrap, а не автоматическим источником доверия. Требуются корректные системные часы.

```json
"dnssec_validation": true,
"dnssec": {
  "auto_update": {"enabled": true, "refresh_hours": 24},
  "trust_anchors": [". 3600 IN DS 20326 8 2 E06D44B80B8F1D39A95C0B0D7C65D08458E880409BBC683457104237C7F8EC8D", ". 3600 IN DS 38696 8 2 683D2D0ACB8C9B712A1948B27F741219298D0A450D612C483AF444A4C0FB2B16"],
  "exempt_zones": [],
  "max_nsec3_iterations": 150,
  "timeout_seconds": 15,
  "ignore_cd": false
}
```

`exempt_zones` отключает проверку для явно указанных суффиксов и их поддоменов; корневое исключение запрещено. Для частной forward/stub-зоны можно установить собственный доверенный ключ вместо исключения. Пустой список anchors восстанавливает встроенные корневые DS. Лимит NSEC3 допускает 0–500 итераций; значение 0 означает отсутствие дополнительных итераций, а не отключение лимита. Тайм-аут — 5–30 секунд.

При `ignore_cd: false` запрос CD=1 возвращает диагностические непроверенные данные без AD и использует отдельный кеш. С `ignore_cd: true` проверка выполняется и для CD=1; AD для такого клиента всё равно не выставляется. AD возвращается только для secure-ответа при CD=0 и DO=1 либо AD=1 в запросе. Проверка выполняется также для клиентов без DO; служебные DNSSEC RR удаляются из их ответов, если не запрошены явно. TTL ограничен сроком действия подписей и всей цепочки доверия; bogus не кешируется.

Криптографические операции и NSEC3-хеширование имеют ограниченные бюджеты и параллелизм. Проверенные ключи кешируются отдельно для каждого маршрута/представления. Prometheus публикует `ghole_dnssec_validation_total{state}`; обзор показывает secure/insecure/bogus и обходы CD/исключения. В журнале ошибки проверки отмечаются `DNSSEC_BOGUS`.

Локальные primary-зоны, split RRset и блокировки остаются административной политикой и AD не получают. Создание подписанных authoritative-зон, ротация собственных KSK/ZSK и AXFR/IXFR — отдельные последующие задачи. DNSSEC не шифрует трафик; для шифрования используйте DoH/DoT.

### Автоматическое сопровождение корневых ключей

`dnssec.auto_update.enabled` включает фоновые проверки, `refresh_hours` (1–360, по умолчанию 24) задаёт верхнюю границу интервала. Фактический интервал также ограничен половиной исходного TTL DNSKEY и оставшегося срока RRSIG, максимумом 15 суток и минимумом один час. Повторы после ошибки назначаются по правилам RFC 5011. Кнопка проверки и перезапуск не обходят сохранённое расписание. Настройки применяются без перезапуска.

Новые поддерживаемые SEP-ключи проходят `AddPend`: не менее 30 суток либо исходного TTL, если он больше, затем требуется ещё один проверенный DNSKEY RRset с ключом. Исчезновение кандидата или отзыв всех первоначальных подписантов сбрасывает ожидание. `Missing` остаётся доверенным. Отзыв требует REVOKE и собственной подписи ключа над полным DNSKEY RRset; он действует сразу. После отсутствия отозванного ключа в течение 30 дней состояние переходит в `Removed`, но запись запрета остаётся, чтобы ключ не появился снова.

Состояние, первоначальные anchors, подписанты кандидатов, таймеры, ошибки и расписание сохраняются отдельно в `ghole_dnssec_managed` SQLite/PostgreSQL с собственной CAS-ревизией. Фоновое обновление не меняет конфигурационный ETag. Пауза останавливает опрос, сохраняя выученные anchors и отзывы; обнаруженные в свежих DNSKEY-ответах отзывы обрабатываются и при паузе. Изменять первоначальные корневые строки после инициализации запрещено; частные trust anchors остаются редактируемыми. Автоматического сброса в начальный набор при повреждении состояния нет. Для переноса и резервного копирования требуется полная база, включая `ghole_dnssec_managed`: JSON-экспорт конфигурации не заменяет копию состояния RFC 5011.

При изменении доверия кеши заменяются атомарно. Между аутентификацией отзыва и его записью в SQL действует защитный барьер: старый AD-ответ не выдаётся даже при задержке записи. Обычные DNS-запросы используют память; постоянная запись требуется только при редком обнаружении нового отзыва. При ошибке сохранения или незавершённой после аварии проверке действует отказ в проверке до восстановления состояния и аутентифицированного опроса. Если все корневые anchors отозваны, GHole применяет локальную политику SERVFAIL вместо автоматического перехода на непроверенные ответы; необходимо административное восстановление доверия вне RFC 5011.

Обзор и настройки показывают состояния ключей, время обнаружения, срок ожидания, ошибки, последнюю и следующую проверку. Prometheus экспортирует `ghole_dnssec_rfc5011_enabled`, `initialized`, `active_anchors`, `last_success_timestamp_seconds`, `next_probe_timestamp_seconds`, `error` (с общим префиксом `ghole_dnssec_rfc5011_`) и `ghole_dnssec_rfc5011_keys{state}`. Сопровождаются корневые ключи RSA/SHA-1, RSA/SHA-256/512, ECDSA P-256/P-384 и Ed25519; неподдерживаемые алгоритмы не принимаются как управляемые anchors. Частные anchors автоматически не обновляются.

Проверки и обновление сервера: [отчёт v0.3.0](docs/rfc5011-test-2026-11-05.md). Протокол: [RFC 5011](https://www.rfc-editor.org/rfc/rfc5011.html). Долгие периоды ожидания проверяются локальными тестами с управляемым временем; часы и интервалы работающего сервера для тестов не изменяются.

Интернет-интеграция запускается отдельно: `GHOLE_DNSSEC_LIVE=1 go test ./internal/core -run TestDNSSECLive -v`. Основной набор тестов использует локальную подписанную иерархию и не зависит от Интернета. [Протокол проверки v0.2.0 и обновления dev.kislovs.ru](docs/dnssec-test-2026-11-05.md).

## API

Все `/api/*` требуют `Authorization: Bearer <admin-token>`:

- `GET /api/status`, `GET /api/config`, `GET /api/logs?page=1&page_size=25&anchor=...`.
- `PUT /api/config` — JSON и `If-Match` из ETag последнего GET.
- `POST /api/zone/import?name=example.` — тело с zone file, возвращает массив записей для редактора.
- `GET /api/zone/export?id=0` — сохранённый primary zone file.
- `POST /api/feed/refresh?id=0` — загрузить источник по URL.
- `POST /api/feed/import?id=0` — импортировать список / gzip в существующий источник.

Конфигурация содержит секреты подписок и списки доменов, доступна только администратору. Журнал не сохраняется на диск.

## Производительность и UDP-воркеры

`udp_workers: 0` автоматически выбирает на Linux до 16 сокетов по доступному Go параллелизму; на других ОС используется один. На Linux можно задать 1–64 через веб-настройки. Изменение требует перезапуска; обзор показывает фактическое число. Воркеры используют SO_REUSEPORT, общий кеш, индексы зон и журнал в одном процессе. Даже с одним сокетом обработчики запросов работают параллельно; число воркеров не задаёт число потоков ОС. Больше сокетов не гарантирует больший QPS.

Общий путь обработки избегает лишних таймеров и форматирования журнала. Пагинация копирует только запрошенную страницу. SQL остаётся вне пути DNS-запроса. Результаты, включая сценарии без ускорения, доступны в [отчёте стенда](benchmarks/2026-11-05/performance/README.md). `scripts/performance-lab.py` запускает ограниченный изолированный стенд; его нельзя направлять на рабочие порты или применять как оценку абсолютной мощности сервера.
