# Устройство GHole и следующие этапы

## Существующая реализация

`cmd/ghole` отвечает за загрузку конфигурации, открытие UDP/TCP/HTTP сокетов, токен администратора и корректное завершение по сигналу. `internal/core` содержит подготовку конфигурации, split views, primary answers, блокировки, кеш, forward/stub/iterative resolution и импорт. `internal/storage` реализует SQLite / PostgreSQL с отдельными таблицами записей, пакетными вставками, транзакциями и ревизией. `internal/transport` содержит входящие DoH / DoT серверы. `internal/telemetry` собирает системные показатели в фоне, хранит ограниченную историю графиков и экспортирует Prometheus. `internal/web` содержит защищённый API и встроенные статические ресурсы.

`Engine` публикует `runtimeState` через `atomic.Pointer`. Снимок не меняется после публикации. Настройки для редактирования возвращаются глубокой копией. Кеш и группа singleflight принадлежат конкретному поколению конфигурации: старый выполняющийся запрос может завершиться со старым снимком, но не заполнит кеш нового поколения. Изменение настроек не держит глобальный mutex в DNS-пути. Новый снимок публикуется только после успешной SQL-транзакции. Настройки сетевых адресов и TLS помечаются как ожидающие перезапуска.

Разрешение зависит от фактического IP источника. Представления выбираются по имени зоны и префиксу IP; значения EDNS Client Subnet не участвуют в политике. Ключ кеша включает имя, тип запроса, DO/CD и ID представления внутри поколения. Если в будущем появятся индивидуальные политики клиентов, их ID также должны войти в ключ кеша и singleflight.

Статистика использует атомарные счётчики. Кольцевой журнал защищён отдельным mutex; запись журнала можно отключить. При росте нагрузки его следует вынести в ограниченную асинхронную очередь перед серьёзным ростом нагрузки. Потеря событий под нагрузкой должна быть видима отдельным счётчиком, а не блокировать ответы DNS.

## Локальный DNSSEC-валидатор

`internal/dnssec` строит цепочку доверия независимо от AD upstream. Для криптографической проверки RRset и доказательств NSEC/NSEC3 используются примитивы `github.com/semihalev/sdns/middleware/resolver/dnssec`; его сервер и фоновые службы не запускаются. Выбор маршрута, цепочка DS/DNSKEY, начальные anchors, кеши, политика CD и границы затрат реализованы в GHole.

Для каждого имени последовательно проверяются родительские DS: подписанный DS требует подходящего DNSKEY и подписи DNSKEY RRset именно ключом, совпавшим с DS. Подписанное отсутствие DS различает unsigned delegation и отсутствие zone cut. Неподдерживаемый набор DS и NSEC3 opt-out не дают secure. Отсутствие доказательства не превращается в insecure. Неподписанные закрытые зоны требуют явного исключения или частного trust anchor.

Ответ проверяется по фактическому пути CNAME/DNAME; синтезированный CNAME допускается только при корректном подписанном DNAME. Удаляются посторонние Answer/Additional, authority ограничивается проверенными записями нужного подписанта. Проверяются wildcard, SOA и доказательства отрицательного ответа на конечном имени. AD отражает весь путь, включая переходы между зонами.

Кеш состояния доверия ограничен 4096 именами на snapshot, ключ включает маршрут/представление, повторная работа объединяется singleflight. Время жизни ограничено TTL DS/DNSKEY/доказательств и RRSIG expiration. Основной кеш хранит локально проверенный AD до финального формирования ответа клиенту и повторно проверяет период подписи при чтении. DO/CD входят в ключ; изменение настроек создаёт новые кеши. Bogus не сохраняется.

Одна проверка ограничена 96 вспомогательными запросами, 48 уровнями цепочки, 16 alias-переходами, 128 проверками подписи и DS digest, 256 NSEC3-хешами, 8 кандидатами ключей/подписями на RRset и 512 RR на пакет; криптографический параллелизм ограничен 32 операциями. Общий сетевой бюджет — 256 обменов. Лимит итераций NSEC3 и тайм-аут настраиваются через панель. Превышение бюджета приводит к отказу проверки, а не к обходу.

Корневые DS включены в бинарник; дополнительные DS/DNSKEY и исключения хранятся в конфигурации SQL. IANA HTTPS используется только для административного bootstrap. `internal/dnssec/managed.go` сопровождает корневые ключи по RFC 5011. Отдельная SQL-запись с CAS хранит состояния AddPend/Valid/Missing/Revoked/Removed, первоначальных подписантов, таймеры и расписание; фоновый опрос не меняет ETag конфигурации. Намерение сетевой проверки записывается до запроса, незавершённое после аварии состояние не используется до повторной аутентификации. Отзывы из свежих ответов обрабатываются также пассивно. Перед записью аутентифицированного отзыва блокируется использование старого доверия, после записи атомарно меняются snapshot, валидатор и кеш. Epoch-барьер отвергает ответы незавершённых запросов со старым доверием. Обычные запросы не обращаются к SQL; редкое событие отзыва требует постоянной записи. Пауза опроса не возвращает bootstrap anchors, а пустой управляемый набор не заменяется начальными ключами. RFC 5011 реализован для корневого trust point; подписание primary-зон пока не реализовано. Детерминированные тесты проверяют подмены RRset/DS/DNSKEY, rogue self-signed key, время подписей, aliases, wildcard, отрицательные доказательства, opt-out и CD/cache; интернет-тест включается отдельно.

## Развитие производительности

До утверждения целевых QPS/p99 нужен воспроизводимый стенд и профиль нагрузки: архитектура CPU, число ядер, память, размер фидов и зон, число views, доля кеша, распределение клиентов, UDP/TCP/DO и запросов в секунду.

Следующие оптимизации по результатам профилирования:

- Отдельные кеши NS/delegation, NS address и RRset; QNAME minimization, устойчивый выбор NS и adaptive timeouts.
- Пул UDP-сокетов с безопасным сопоставлением ID/question и непредсказуемыми исходными портами, ограниченный пул TCP; сохранять защиту от spoofing.
- Pending resolution и saturation; асинхронное журналирование при необходимости по профилю. Гистограмма latency и фиксированные причины ответов уже экспортируются в Prometheus.
- Prefetch популярных RRsets с jitter, ограниченный serve-stale, отрицательный кеш с корректными DNSSEC-доказательствами.
- Ограничение частоты по клиентам и сетям, защита от random-subdomain flood и дорогостоящих DNSSEC-запросов.
- Отделить метаданные конфигурации от больших наборов фидов в административном API. Сейчас JSON содержит сами списки; при миллионах записей веб-редактирование и сохранение потребляют лишнюю память.
- Потоковая сборка и атомарная публикация индексов фильтрации; обновления по расписанию с backoff/jitter, ETag/Last-Modified и проверкой подписанных офлайн-манифестов.

Поставка остаётся одним исполняемым файлом; конфигурация и пользовательские данные сохраняются отдельно. SQLite использует pure Go драйвер без CGO; PostgreSQL требует внешний сервер. Обе реализации включены в один бинарник. SQL отсутствует в пути DNS-запроса. Сохранение обходит неизменившиеся наборы записей; метаданные и изменения сохраняются атомарно. Постоянная синхронизация снимков между несколькими процессами пока не реализована.

## Совместимость и эксплуатация

Перед промышленной эксплуатацией нужны fuzz-тесты DNS/zone/feed parsers, проверка RFC compliance, нагрузочные тесты на Linux amd64/arm64 и Windows, проверка graceful restart, тестирование большого числа TCP-соединений и аудит резолвера. Нужны AXFR/IXFR/NOTIFY и secondary-зоны, если потребуется полноценная миграция с BIND; текущая версия их не реализует.

Интеграция с feed.kislovs.ru требует документации endpoint, авторизации, структуры ответа, обновлений, формата и подписей офлайн-пакета. До этого существует только универсальный HTTP(S) адаптер для текстовых списков / gzip. Нельзя считать его проверенной интеграцией с сервисом.

## Наблюдаемость и транспорты

UDP/TCP/DoT входят через `ServeDNSAs`, DoH — через `AnswerAs`; оба вызывают общий `Resolve` и общий наблюдатель. Метки транспорта и результата ограничены, Prometheus handles подготовлены заранее. Наблюдение не собирает ОС-метрики, не выполняет SQL и не выделяет память на каждый запрос. Системный сбор выполняется раз в 5 секунд отдельно; история графиков ограничена 180 точками. Блокировки считаются по запросам, а не по числу доменных записей.

DoH использует отдельный HTTPS listener с HTTP/2 и RFC 8484 wire format; DoT — TLS listener с TCP framing. Оба используют общий сертификат с минимумом TLS 1.2. В заголовки прокси не встраивается доверие: split DNS зависит от непосредственного IP соединения. Автоматический ACME, динамическая перезагрузка сертификатов и шифрованные upstream пока не реализованы.

## Сплит RRset и страницы журнала

У primary-зон есть `record_views`: CIDR-группы переопределяют RRset отдельных имён. Для каждой пары префикс/затронутое имя заранее строится эффективный набор типов, объединяющий общие данные и все подходящие родительские префиксы. Индекс содержит только затронутые имена, а не полную копию зоны для каждого CIDR. На запросе используется поиск самого длинного подходящего префикса. Пустые узлы и wildcard также учитывают видимость клиента. CNAME при слиянии заменяет другие типы владельца.

SQL-схема версии 2 хранит группы и записи в отдельных таблицах; автоматическая миграция версии 1 сохраняет базовые зоны и записи. Хеши наборов позволяют не перезаписывать неизменившиеся сплит-записи.

Журнал ограничен `query_log_limit` и имеет монотонные ID внутри процесса. API возвращает страницы с верхним ID-якорем, чтобы новые запросы не сдвигали выборку. Переполнение кольца может вытеснить старые строки даже закреплённой выборки. Обзор запрашивает только восемь строк; журнал загружает только выбранную страницу. Долговременного хранилища журнала пока нет.

## Горячий путь и UDP (v0.4)

Linux запускает группу UDP listeners с SO_REUSEPORT, общим Engine и независимыми readers. Привязка всех сокетов завершается до начала обслуживания; ошибка закрывает всю группу. GOMAXPROCS управляет параллелизмом Go независимо от числа сокетов. TLS/TCP/DoH используют обычную параллельную обработку соединений.

Таймер разрешения создаётся внутри singleflight только при внешнем промахе кеша. Возврат из кеша по-прежнему копирует RR, уменьшает TTL и проверяет срок подписи; вопрос и OPT формируются для текущего клиента. Ключи включают DO/CD и view; публикация доверия RFC 5011 сохраняет защитный барьер.

Кольцевой журнал хранит время, IP и тип в числовом виде. Форматирование выполняется после копирования выбранных строк вне mutex. Непрерывные ID позволяют вычислить смещение страницы за O(1); копирование и форматирование занимают O(размер страницы). Пропусков из-за неблокирующего enqueue нет.
