# DNSSEC-кеш и конкуренция воркеров — 6 ноября 2026

Сравнение baseline d3ec6c9 / установленного gdns v0.5.0 с кандидатом v0.6.0. Изменены только подготовка приватного EDNS-ответа из кеша и организация ограниченного журнала. Алгоритмы криптографии, сроки подписей, DO/CD, разделение views и барьер отзыва не ослабляются.

## Профили

Linux amd64, Ubuntu на dev.kislovs.ru, 3 vCPU; тестовый исполняемый файл запускается отдельно, рабочая служба не профилируется и не получает тестовую конфигурацию. CPU/memory/mutex/block снимаются в BenchmarkAnswerFastPath/SecureCache/log=true с GOMAXPROCS=3, benchtime=5s, mutexprofilefraction=10, blockprofilerate=1000000. Тест включает Prometheus и журнал, но не сеть. Ответ заранее помещён в кеш; подпись проверяется на допустимость времени, а криптографическая валидация в этом микробенчмарке не измеряется. Профили включают калибровку Go benchmark, поэтому длительность записи больше benchtime. Top-файлы содержат функции и агрегаты, без рабочих конфигураций и токенов.

В baseline 666.76 мс суммарного выборочного ожидания mutex отнесены к appendLog; в новом профиле этот стек не выделяется выше порога отображения 1.39 мс. Это эксперимент без параллельных читателей журнала, не оценка p99 рабочего сервера. runtime.unlock в профиле включает внутренние блокировки Go и не означает блокировку кеша приложения. Копирование сообщения в baseline составляло около 23% CPU; выделение/освобождение памяти также заметно в профиле.

Прежние 8 выделений / 464 байта на EDNS secure-cache hit стали 6 / 448. Сохраняется глубокое копирование RR. Память ячейки кольца журнала выросла приблизительно с 88 до 128 байт: около +0.4 МБ для 10 тыс. и +4 МБ для 100 тыс. строк.

## Микробенчмарки

Непрофилированные прогоны Linux: benchtime=1s, count=3, cpu=1,3, журнал включён/выключен. Полные выводы baseline-linux-bench.txt и candidate-linux-bench.txt. Медиана secure-cache с журналом: 2825 → 2375 нс на одном CPU, 2166 → 2110 нс при трёх. Общий VPS даёт заметный разброс; это не обещание фиксированного роста сетевого QPS. Дополнительные native-выводы относятся к Apple M4; baseline-native сравнивает только включённый журнал.

## Сетевое сравнение

scripts/performance-lab.py --suite dnssec-cache --repeats 3 запускает изолированные UDP listeners на 127.0.0.1:1153 с отдельной базой, миллионным синтетическим blacklist, частной подписанной зоной и её отдельным якорем. Рабочая конфигурация и managed state не меняются. Варианты: before-one, after-one, before-three, after-three. Целевые темпы 10/20/30 тыс. запросов/с, три повтора по 5 секунд; затем три повтора холодной DNSSEC по 500 запросов/с с отключённым кешем ответов. Генератор и подписанный fixture делят CPU с сервером и другими службами. Целевой темп не равен достигнутому. Измерений p95/p99 здесь нет.

Сетевые результаты добавляются после завершения матрицы. Контрольная сумма испытанного кандидата Linux amd64: 90c8910b712c9269671edec625cb1520905455b877841bc35b71446e0de44933; подписанный fixture: 5c7377fe083817399ed86846eb95954729987530cb8c96328ce6ba885839672a.

## Корректность

Race-тесты всего проекта, go vet, интеграция PostgreSQL 16; 20 повторов конкурентной записи/resize/снимков журнала и независимости клиентских OPT/RR. Проверены истёкшие и ещё не действующие RRSIG. Живые DNSSEC/RFC 5011 тесты forward/recursive прошли; их вывод сохранён в live-check.txt. Полный 30-дневный rollover на этом стенде не ускорялся и не имитируется этими живыми проверками.
