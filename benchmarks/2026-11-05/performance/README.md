# Производительность GHole v0.4.0 (2026-11-05)

Сравнение с v0.3.0: оптимизация общего пути ответа, журналирования и UDP listeners. Публичные результаты не содержат конфигураций, токенов и баз данных.

## Методика

Микробенчмарки: `go test ./internal/core -run '^$' -bench 'BenchmarkAnswerFastPath|BenchmarkJournalPage100000' -benchmem -benchtime=500ms -count=3 -cpu=1,4`. Файлы micro-before/after содержат полный вывод. AnswerAs включает Prometheus, DNSSEC-конфигурацию и выбранный режим журнала, но не включает сеть и TLS. SecureCache использует заранее помещённый тестовый ответ и измеряет обработку кеша, а не криптографическую проверку. Для журнала дополнительно опубликованы journal-before/after с реалистичными строками IP, времени и типа; исходный micro-прогон использовал пустые поля этих строк.

Сетевой стенд: dev.kislovs.ru, Ubuntu 24.04, Linux 6.8, 3 vCPU. Генератор, подписанный тестовый upstream и изолированный GHole делят один сервер с рабочими службами. Это сравнительный эксперимент, не измерение мощности выделенного DNS-сервера. Рабочие порты, настройки, RFC 5011 и часы не менялись. Включены журнал, Prometheus и DNSSEC. Чёрный список содержит миллион синтетических доменов; split RRset задан для /28. Использован scripts/performance-lab.py и cmd/ghole-bench-upstream, подписывающий частную тестовую зону с отдельным якорем. Публичные корневые ключи не заменяются.

before — установленный v0.3.0, один UDP listener. after — кандидат v0.4.0, автоматические три UDP-воркера. after-one — тот же кандидат с одним воркером. Каждый вариант: четыре UDP-сценария × четыре целевых темпа (5/10/20/30 тыс.) × два повтора по 5 секунд, TCP 4 тыс. и DoT 2 тыс. по два повтора, два HTTP/2-прогона по 20 тыс. запросов и два прогона холодной DNSSEC по 500 запросов/с с отключённым кешем ответов. TLS на сервере остаётся включён; доверие сертификату проверяется отдельным HTTPS probe. Генератор DoT dnsperf сам по себе не является проверкой сертификата. Максимум 128 незавершённых запросов ограничивает достигнутый QPS; целевой темп нельзя считать достигнутым.

## Результаты

Один CPU, медиана трёх повторов AnswerAs с журналом:

- Primary: 650.2 → 299.4 нс; 13 → 5 выделений, 629 → 264 байта.
- Split: 669.6 → 324.5 нс; 13 → 5 выделений, 629 → 264 байта.
- Blocked: 545.5 → 233.0 нс; 8 → 2 выделения, 484 → 168 байт.
- Cache: 832.9 → 389.1 нс; 17 → 7 выделений, 878 → 352 байта.
- SecureCache: 900.0 → 428.6 нс; 18 → 8 выделений, 991 → 464 байта.

Страница из 25 строк в журнале на 100 000 строк: 155.9 → 2.35 мкс (медиана одного CPU, реалистичные время/IP/тип). Число выделений при чтении страницы выросло из-за отложенного форматирования, но обработка DNS избегает этих выделений, а полный проход по кольцу устранён.

Для сети ниже указано среднее двух повторов before → after, фактические QPS и средняя задержка при максимальном целевом UDP-темпе:

- primary: 24696 → 25985 QPS; 4.283 → 3.849 мс.
- split_28: 20544 → 24077 QPS; 5.127 → 4.125 мс.
- blocked_million: 23057 → 25744 QPS; 4.540 → 3.823 мс.
- secure_cache: 22242 → 20335 QPS; 4.849 → 5.153 мс.

Все 120 прогонов завершились без потерь. Проверены ожидаемые коды ответов, split-адрес и AD у подписанного ответа. Несколько воркеров помогают части нагрузок; на максимальном темпе SecureCache стал медленнее, а при 20 тыс. показал улучшение. Холодная DNSSEC заметного выигрыша не показала. DoH в среднем 7184 → 8273 запросов/с, но повторяемость на общем сервере недостаточна для обещания фиксированного процента. Все результаты, включая вариант одного воркера, опубликованы полностью. Измерений p99 нет; среднее и максимум не заменяют p99. Для настройки промышленной установки нужен отдельный генератор и более длительные повторы с её реальным профилем.

## Проверка корректности

`go test -race ./...`, `go vet ./...`, PostgreSQL 16 integration; дифференциальный fuzz границ DNS-имён, якорная пагинация при переполнении/изменении размера, дедлайн upstream, UDP-группа и конфликт bind. Живые DNSSEC/RFC 5011 проверки forward/recursive включают secure, insecure, bogus, DS, NODATA и NXDOMAIN. RFC 5011 hold-down не сокращается. Развёртывание и последующая проверка транспортов описаны отдельно в журнале обновления.
